> Implementation plan for `quarkscharm-v1`. Executors read `proposal.md`,
> `design.md`, `specs/*/spec.md` and `docs/quarksup-api.md` first. Every
> task ends with the check that proves it; `bun run check` (lint, fmt:check,
> typecheck, test:unit, ds:check, spec:check) must be green before a commit
> is pushed. Commits: Conventional Commits, STE100 wording, trailer
> `Change: quarkscharm-v1`. Everything lands on `main`.
>
> Global constraints (from the specs and design):
> - Node >= 24, bun as package manager, Nuxt 4 `app/` layout, oxlint + oxfmt,
>   vue-tsc via `nuxt typecheck`, `bun test` for units, Playwright for e2e.
> - No TS enums, no DTO layer, plain objects with stable shapes, English-only
>   in-source artifacts, comments only when load-bearing (`.claude/rules`).
> - Nothing tenant- or user-specific in code: tenant, employee id, nature ids
>   and workflow sequence ids come from the API at runtime.
> - Dates are `YYYY-MM-DD` strings plus `am`/`pm` flags; API dates are read
>   by their first 10 characters and hour, written as `${date}T${hh}:00:00Z`.
> - Colours only through design-system tokens (`var(--…)`), checked by
>   `ds:check`.
> - quarksUp data never touches `localStorage`; only tenant, token and UI
>   preferences do.
>
> Review focus (inputs the specs do not name; each has a test in the task
> that owns it):
> - A pasted token with surrounding whitespace or a leading `Bearer ` must
>   still connect (task 5.1).
> - A request that spans New Year (29 Dec – 2 Jan) must render in both
>   years (task 3.2, 7.2).
> - A preview that splits one painted run into several segments (holiday in
>   the middle) must show every segment and submit the run once (task 8.3).
> - A year change while previews are in flight must drop the stale
>   responses, not paint them on the new year (task 8.2).
> - A planner answer without `nonWorkingDates` or with an empty `absences`
>   list must render a plain grid, not crash (task 7.1).
